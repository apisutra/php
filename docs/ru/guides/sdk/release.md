# Документация и выпуск SDK <a id="section-1"></a>

Цель — чтобы потребитель установил SDK, создал клиента, вызвал операцию и обработал
ошибку по опубликованной инструкции. Перед выпуском пройдите [покрытие](coverage.md).

## Структура документации SDK <a id="section-2"></a>

| Слой | Содержание |
| --- | --- |
| README | Назначение, требования, установка, первый вызов, ссылки на задачи |
| Руководства | Реальные сценарии и проверяемые примеры |
| Справочник SDK | Операции, параметры и отличия конкретного провайдера |
| Словарь, если нужен | Краткие определения провайдерских понятий со ссылками |
| CONTRIBUTING/development | Изменение самого SDK, тесты, архитектура и выпуск |
| Миграция и changelog | Изменение совместимости и действия потребителя |

Группируйте файлы по задаче или ресурсу. Если документ растёт, выделяйте самостоятельный
сценарий либо контракт; не делите последовательный текст на части с номерами.
Архитектурные схемы полезны разработчику SDK, но не должны быть обязательным чтением
для пользователя его API. Агенту передавайте общий пользовательский маршрут.

## Что описать у операции <a id="section-3"></a>

Укажите назначение, публичный вызов, обязательные входные данные, тип результата,
ошибки и специальные режимы. В примере должны быть понятны конфигурация, транспорт,
auth scope и подготовка DTO. Версия API, sandbox, ограничения доступа и платность
фиксируются по подтверждённым данным провайдера.

При пагинации укажите способ получения страниц и общий лимит. Для длительной операции
объясните Ready/Pending, token и await. Для файлов — destination и владение ресурсами.
Сохраняйте известные ограничения рядом с соответствующим вызовом.

Общий контракт ApiSutra не копируйте: ссылайтесь на нужный раздел
[справочника](../../reference/README.md), описывая только выбор и особенности своего SDK.

## Порядок подготовки <a id="section-4"></a>

1. Зафиксируйте пользовательские задачи и поддержанные операции.
2. Согласуйте имена терминов, ресурсов, DTO и enum с кодом.
3. Подготовьте один исполняемый пример; README и тест должны использовать тот же источник.
4. Опишите самостоятельные сценарии и свяжите их с владельцами контрактов.
5. Добавьте инструкции разработчика SDK отдельно, затем проверьте навигацию и размеры.

При изменении операции одновременно обновляйте её пример и документацию. Новое
понятие получает определение, новое поведение — контракт и проверку. Не храните
конкурирующие алгоритмы в README, словаре и справочнике.

## Проверка выпуска <a id="section-5"></a>

- Установка в чистом приложении проходит с runtime-зависимостями; autoload видит классы.
- Первый пример исполняется из опубликованного пакета, без скрытых переменных и binding.
- Поддерживаемые окружения проверены: standalone обязательно для заявленной поддержки,
  Laravel и особые транспорты — при наличии соответствующей интеграции.
- Fake-тесты воспроизводят запрос, DTO, ошибки и используемые сложные сценарии.
- Live-тесты запускаются явно и не превращают обычную установку в обращение к API.
- Ссылки и якоря существуют; примеры работают из установленного SDK без файлов его репозитория.
- В репозитории и архивах нет секретов; фикстуры обезличены.
- Версия и миграция отражают совместимость, особенно изменения strict, формы и wire.

[Records SDK](../../examples/sdk.md) показывает небольшой комплект README,
исходников, Composer-манифеста и фикстур. Его можно установить и использовать как основу
с namespace и данными своего SDK. При поставке
[Laravel-интеграции](https://github.com/apisutra/laravel/blob/master/docs/ru/guides/sdk/laravel.md) проверьте discovery из установленного пакета,
defaults без публикации, overrides приложения и `config:cache`.
