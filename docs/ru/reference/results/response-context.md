# Контекст ответа после отказа <a id="section-1"></a>

После исчерпания повторов последний HTTP-ответ проходит обычный error mapping.
Например, 503 остаётся `service_unavailable`, включая ответ с HTML или испорченным JSON.
Для 400 используется `bad_request`, для остальных немаппируемых 4xx — `client_error`;
ответ и его raw body сохраняются. Строковый `message` из JSON используется как сообщение,
иначе применяется `HTTP <status>`. Если последняя HTTP-попытка завершилась сетевым сбоем,
ответ предыдущей попытки не подставляется вместо отсутствующего текущего ответа.

Для запроса, сначала получившего HTTP 500, различайте окончательную причину
и контекст ответа. `ExecutionResult::response` и `RequestError::response` согласованы:

| Чем затем завершается исполнение | Код ошибки / reason | Ответ |
| --- | --- | --- |
| Ещё одна HTTP-ошибка | Код, соответствующий её статусу | Новый ответ |
| Ошибка соединения | `connection_failed` | null |
| Транспортный timeout при оставшемся общем бюджете | `timeout`, без `execution_deadline_exceeded` | null |
| Общий deadline до повтора или во время HTTP | `timeout` / `execution_deadline_exceeded` | Предыдущий 500 как контекст |
| Локальный отказ квоты или cooldown | `rate_limited` / `local_rate_limit_exceeded` или `server_cooldown_active` | Предыдущий 500 как контекст |
| Сбой backend квоты/cooldown | `execution_error` / `rate_limit_backend_error` или `cooldown_backend_error` | Предыдущий 500 как контекст |

Классифицируйте окончательный отказ по code, reason, stage и исключению: сохранённый
HTTP-статус сам по себе не определяет причину. Auth dependency также может передать
последний ответ родительскому исполнению, поэтому сохранённый контекст не обязательно
является последним ответом исходного запроса. Цепочка исключений сохраняет исходные
причины транспортных/backend-сбоев там, где они есть.
