# Timeout, delay и общий дедлайн <a id="section-1"></a>

Штатный транспорт применяет `timeout = 30` и `connectTimeout = 10` секунд без
дополнительной настройки. Общего лимита на всё выполнение по умолчанию нет.

## Таймаут одной HTTP-попытки <a id="section-2"></a>

```php
use ApiSutra\Config\ClientConfig;

$config = new ClientConfig(
    baseUrl: 'https://api.example',
    timeout: 30,
    connectTimeout: 10,
);
```

`timeout` ограничивает соединение и получение ответа целиком. `connectTimeout`
ограничивает установление соединения, включая TLS handshake. Эти интервалы
не складываются: соединение входит в общий таймаут попытки.

Каждое поле разрешается независимо: runtime `withTimeout()` → `#[Timeout]` →
`ClientConfig`. Отсутствующее значение и `null` означают наследование. Например,
`withTimeout(5)` сохраняет connect timeout атрибута или клиента; при отправке
он ограничивается таймаутом всей попытки. Повторный `withTimeout(20)` сбрасывает
прежний runtime connect override к наследованию.

`0` отключает соответствующий SDK-лимит; отрицательные значения и переполнение
при переводе секунд в миллисекунды дают ошибку конфигурации. Эти правила одинаковы
для конфига, атрибута и runtime. Методы runtime возвращают отдельный execution:
используйте возвращённое значение.

```php
$result = $request->withTimeout(5, 2)->send();
$inheritedConnect = $request->withTimeout(5)->send();
```

## Необязательный общий бюджет <a id="section-3"></a>

```php
use ApiSutra\Config\RetryConfig;

$config = new ClientConfig(
    baseUrl: 'https://api.example',
    retry: new RetryConfig(attempts: 1, totalTimeoutMs: 5000),
);
```

`RetryConfig::totalTimeoutMs` задаётся в миллисекундах. `null` означает отсутствие
общего лимита; положительное значение создаёт абсолютный монотонный deadline при
входе в каноническое исполнение, до пагинации и авторизации. Сдвиги календарных часов его не изменяют.
`attempts: 1` задаёт бюджет без общих повторов. `withoutRetry()` и
`#[Retry(enabled: false)]` отключают retry, сохраняя бюджет клиента.

Время авторизации, HTTP, delay, rate-limit wait, backoff, Retry-After, refresh и
ожидания refresh lock расходует один бюджет. Дочерние запросы auth/composite/depends-on
наследуют срок родителя; собственный меньший лимит может его сократить. Независимые
вызовы без внешнего срока получают новые бюджеты. Batch в целом и await/polling не получают отдельный
общий deadline: лимиты действуют на составляющие выполнения и переданный контекст.

Сбор пагинации all/pages/range делит один бюджет на весь обход: три последовательные
страницы по 400 мс не завершатся с totalTimeoutMs=1000. Ленивый iterator сохраняет новый
бюджет клиента на страницу; withDeadline задаёт срок всего обхода.
См. [срок пагинации](pagination.md#section-23).

Перед HTTP таймаут ограничивается остатком бюджета, даже при `timeout: 0`.
Например, 250 мс передаются штатному адаптеру как 0,25 секунды, без округления до
безлимитного нуля. Если обязательное ожидание не оставляет времени для продолжения,
SDK сразу завершает выполнение; Retry-After не сокращается ради ранней отправки.

Исчерпание бюджета даёт окончательный `timeout` с `reason: execution_deadline_exceeded`
и `stage` в контексте ошибки, а также `ExecutionDeadlineException`. Последний доступный
HTTP-ответ сохраняется для диагностики. Таймаут отдельной попытки допускает безопасный
retry по политике клиента; исчерпание бюджета — нет. Поздний HTTP 200 не становится
успехом и не запускает запись успеха в кеш.

## Общий дедлайн нескольких вызовов <a id="section-4"></a>

Когда приложение выполняет цепочку «создать → загрузить → подтвердить», оно может
передать один срок каждому исполнению. Для запросов с заданным/разрешаемым клиентом:

```php
use ApiSutra\Timing\ExecutionDeadline;

$deadline = ExecutionDeadline::afterMs(1000);

$created = $create->withDeadline($deadline)->dataOrFail();
// Приложение подготавливает следующий запрос по результату предыдущего.
$uploaded = $upload->withDeadline($deadline)->dataOrFail();
$confirmed = $confirm->withDeadline($deadline)->dataOrFail();
```

Объект неизменяемый; отсчёт начинается при `afterMs()`, включая время между send.
Повторная передача объекта ничего не перезапускает. При трёх вызовах по 400 ms
третий HTTP-вызов получает только 200 ms. Этот же остаток ограничивает delay,
rate-limit wait, backoff, Retry-After и auth refresh через существующий budget.

Действующий срок — минимум внешнего, родительского и клиентского `totalTimeoutMs`.
Опция работает без RetryConfig и с `withoutRetry()`. `withoutDeadline()` снимает
только внешний срок конкретного исполнения; остальные пределы остаются. Исходный
request и ClientConfig не меняются, опция не входит в cache identity. Без опции
поведение прежнее; дополнительных зависимостей и настроек клиента нет.

Истёкший срок (включая `afterMs(0)`) даёт `timeout` с
`reason: execution_deadline_exceeded`, `stage: started` до HTTP/auth/cache I/O
и execution hooks. Отрицательное значение или переполнение отклоняются.
Ожидание, равное остатку или превышающее его, не выполняется. Сборка клиента
не становится частью отменяемой операции.

Используются монотонные часы. Штатные SystemClock совместимы между клиентами
текущего процесса; в тестах один ClockInterface передавайте клиенту и
`ExecutionDeadline::afterMs(1000, clock: $clock)`. Разные пользовательские объекты
часов отклоняются как `configuration_error`. Дедлайн не предназначен для сохранения
и передачи в другой worker. Бизнес-цикл и решение о следующем запросе принадлежат
приложению; SDK соблюдает переданный срок внутри своих выполнений.

## Граница гарантии и транспорт <a id="section-5"></a>

Штатная интеграция использует Guzzle с cURL; Laravel выбирает адаптер автоматически,
вне Laravel доступен `HttpTransport::createDefault()`. Для этой сборки нужны
`guzzlehttp/guzzle` и `ext-curl`; ядро сохраняет возможность другого транспорта
без Laravel/Guzzle Client. Подробности — в [руководстве транспорта](transport.md).

Произвольный PSR-18 клиент не имеет per-request timeout options. Если транспорт
не может применить ненулевой лимит, включая дефолты, до HTTP возвращается
`configuration_error`. При `timeout: 0`, `connectTimeout: 0` и отсутствии deadline
обычный PSR-18 путь допустим; собственные ограничения HTTP-клиента сохраняются.

Поддерживаемый транспорт прерывает HTTP. Произвольные hooks, валидаторы, cache-store
и пользовательский PHP-код проверяются на границах после возврата управления:
переносимый синхронный PHP не может принудительно остановить их посередине. Уже
начатые побочные эффекты такого кода не откатываются. Часы и sleeper внедряются
только при необходимости, например в тестах; обязательной пользовательской настройки нет.

## Задержка <a id="section-6"></a>

```php
$config = new ClientConfig(
    baseUrl: 'https://api.example',
    delay: 200, // мс перед каждой HTTP-попыткой
);
```

По умолчанию `delay = 0`. Runtime `withDelay()` / `withoutDelay()` переопределяет
задержку. Ожидание входит в общий бюджет, если он задан.

### SleeperInterface <a id="section-8"></a>
Delay, retry и cooldown используют SleeperInterface из конструктора клиента. Штатный
CooperativeSleeper блокирует синхронный вызов и уступает управление внутри async-задач SDK.
Его подмена сама по себе не делает транспортное I/O конкурентным. Тестовый sleeper должен
двигать те же монотонные часы, что используют исполнение и cooldown. RetryDelayPolicyInterface
только вычисляет backoff; pipeline объединяет его с Retry-After и [общим cooldown](cooldown.md)
и выполняет ожидание до получения квоты.

I/O общего cooldown backend расходует тот же бюджет (cooldown_read/cooldown_publish).
Необязательный phpredis-адаптер блокирует поток на ограниченное время и в async-задачах;
см. [таймауты и цену Redis](../integrations/redis.md#cooldown).
