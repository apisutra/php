# Элементы и коллекции пагинации <a id="section-1"></a>

`Paginator::items(): Traversable` позволяет потреблять элементы по мере получения
страниц. Создание итератора не отправляет HTTP и не материализует результаты.
Обычный обход по-прежнему выдаёт страницы. `$paginator` ниже получен от запроса,
уже привязанного к клиенту:

```php
foreach ($paginator as $page) {
    if ($page->isFailed()) {
        break;
    }
    // Проверьте статус, ошибки, HTTP-ответ и метаданные перед чтением data.
}

// Отдельный обход того же источника, теперь с выдачей элементов.
foreach ($paginator->items() as $item) {
    $repository->save($item); // Репозиторий приложения.
}
```

## Три метода items <a id="contracts"></a>

| Метод | Данные и загрузка | Ключи и ошибки |
| --- | --- | --- |
| PaginationItemsContainerInterface::items() | Элементы одной готовой страницы: array или object | Ключи исходного контейнера; контракт доставки ошибок исполнения не задан |
| PaginatedResult::items() | Уже собранный агрегат: array или object, без HTTP | Числовые ключи дописаны, строки уникальны; accessor, не throw() |
| Paginator::items() | Ленивый Traversable элементов; HTTP при потреблении | Позиции 0, 1, … на весь обход; FAILED бросает, PARTIAL отдаёт данные |

Поток сохраняет каждое значение, включая повторяющиеся ID и строковые ключи разных
страниц. Дедупликации нет. Для исходных ключей и диагностики по страницам используйте
результаты страниц. DTO остаётся тем же объектом. Читатель принимает массивы и
итерируемые коллекции, в том числе внутри PaginationItemsContainerInterface.
Null означает отсутствие элементов. Публичные свойства объекта и наличие только
метода toArray не заменяют обход: неитерируемая коллекция даёт `configuration_error`.

Явный DTO::toArray по-прежнему сериализует по выходным правилам DTO. SDK не вызывает
toArray коллекции лишь для перечисления элементов пагинации.

## Ошибка не означает конец списка <a id="errors"></a>

**Страница FAILED бросает исключение через настроенную фабрику результата даже при
throwOnErrors=false.** Иначе неполный список выглядел бы завершённым. Например,
клиент настроен с throwOnErrors=false, а вторая страница завершается ошибкой:

```php
// $paginator использует этот клиент; $processed — прогресс приложения.
$processed = 0;
try {
    foreach ($paginator->items() as $item) {
        $repository->save($item);
        ++$processed;
    }
} catch (Throwable $error) {
    // Прежние сохранения остаются. Отметьте незавершённый обход и обработайте ошибку.
    $reporter->failed($processed, $error);
}
```

Фабрика вызывается один раз независимо от throwOnErrors. Страница PARTIAL отдаёт
данные, как dataOrFail; отсутствие исключения не доказывает отсутствие предупреждений
или ошибок. Для самостоятельной проверки всех статусов и ошибок выбирайте обычный
обход страниц с throwOnErrors=false. Исключение тела цикла остаётся ошибкой приложения.
[Исполняемый пример](../../../example/dto-hydrator/run.php) показывает отказ второй
страницы после выдачи первого DTO.

## Время жизни и память <a id="lifetime"></a>

Каждый обход items() начинается заново. Он использует существующие resolver и guards
page/cursor/offset, retry, auth, квоты и cooldown. Обход последовательный:
concurrency больше единицы отклоняется до HTTP. Предзагрузки нет.
Пустая страница не завершает обход, если метаданные сообщают о следующих страницах.

Клиентский totalTimeoutMs остаётся бюджетом каждой страницы ленивого обхода. Для
общего срока используйте один внешний withDeadline. Собирающие all/pages/range имеют
отдельный [контракт общего бюджета и конкурентности](pagination.md#section-21).

Итератор не накапливает предыдущие страницы или элементы. Сама страница и данные,
удерживаемые приложением, продолжают занимать память. Полное потребление завершает
обход; ошибка извлечения в SDK отмечает его failed. Освобождение незавершённого
генератора отмечает abandoned и не выполняет HTTP. Удержанный Generator после break
сохраняет область до освобождения ссылки. Уже выполненные запросы и изменения
приложения не откатываются.

## Собирающие терминалы сохраняют значения <a id="aggregation"></a>

all(), pages() и range() используют тот же читатель, сохраняя контракт агрегата.
Числовые элементы дописываются в порядке страниц; уникальные строковые ключи сохраняются.
Повтор строки даёт FAILED с code `hydration_error` и reason `pagination_item_key_collision`, без частичного
data агрегата. Полученные результаты страниц остаются доступны через pages().
Partial/IgnoreErrors не превращают локальную ошибку сборки в успешное затирание.
Сам ключ не попадает в диагностику. Повтор строки внутри iterable одной страницы
подчиняется тому же правилу. Если повторы значимы, используйте список.
Это коллизия объединяемых элементов, а не неверная декларация DTO; ключи могут
приходить от провайдера или создаваться коллекцией/фабрикой приложения.

В Laravel [Pagination::collect](https://github.com/apisutra/laravel/blob/master/docs/ru/reference/integrations/pagination.md)
оборачивает этот поток в LazyCollection без второго механизма обхода.
