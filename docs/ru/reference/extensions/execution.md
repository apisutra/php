# Расширение исполнения запросов <a id="section-1"></a>

Для изменения запроса или ответа на определённой стадии используйте [хуки](hooks.md).
Для обёртки всего исполнения, включая batch, composite, авторизацию, пагинацию и poll,
используйте `ClientInterface::execution()`. Каждый клиент реализует этот метод и
возвращает `ClientExecutorInterface` из
`ApiSutra\Contracts\Interfaces\Execution`.

## Контракт исполнителя <a id="section-2"></a>

Оба метода принимают `(RequestInterface $request, RequestRole $role = RequestRole::Root,
?PipelineContext $parent = null, ?ExecutionTrace $parentTrace = null,
?ClientExecutorInterface $dispatcher = null)` именно в этом порядке:

| Метод | Возвращаемое значение |
| --- | --- |
| `execute(...)` | Окончательный `ExecutionResult`, включая `FAILED` |
| `executeAsync(...)` | `PromiseInterface`, fulfilled таким же результатом, включая `FAILED` |

У результата завершены извлечение метаданных, локализация, проверки бюджета и
терминальная диагностика. Обычные ошибки HTTP/DTO/обработчиков остаются каноническими
результатами; `throwOnErrors` и фабрика исключений применяются при публичной выдаче
**после** этой границы. Не вызывайте `throw()` или публичный `send()` для реализации исполнителя.

Throw, reject или fulfilled значением другого типа у стороннего исполнителя нарушают
контракт. Сбой выходит без HTTP retry и преобразования фабрикой исключений.
Конкурентный оркестратор прекращает новые запуски и завершает выданные Promise.
Собственный executor должен продвигать ожидающие Promise в цикле SDK; одной
блокирующей wait-функции Guzzle недостаточно. Штатный executor использует
кооперативный HTTP по [контракту транспорта](../execution/transport.md).

`parent` передаёт зависимому запросу действующий бюджет и контекст родителя.
`parentTrace` только связывает новый запуск; страницы и poll используют его со своими
HTTP-бюджетами. Если переданы оба аргумента, `parentTrace` должен быть trace родителя.
Противоречие даёт `ConfigurationException` до HTTP. Переопределение trace в запросе
сохраняет приоритет. Повтор запроса создаёт новую executionId и отдельный контекст вызова.

## Передача вызова декоратором <a id="section-3"></a>

Декоратор исполнителя передаёт **все пять аргументов**, используя `dispatcher ?? $this`
для последнего. Например, внутри его реализации `execute()`:

```php
return $this->inner->execute($request, $role, $parent, $parentTrace, $dispatcher ?? $this);
```

`executeAsync()` передаёт аргументы аналогично и возвращает полученный Promise.
Так внешний декоратор сохраняется у дочерних операций, включая refresh авторизации
внутри ребёнка composite. В декораторе храните настройки; текущие context/dispatcher
остаются локальными для вызова. Обёртка `ClientInterface` делегирует `execution()` или
возвращает такой декоратор. Наследник `AbstractClient` может переопределить `execution()`
и обернуть `parent::execution()`; при смене транспорта клиента оборачивайте актуальный исполнитель.

Переопределение публичных `send()`/`sendAsync()` оборачивает только прямые вызовы
пользователя. Внутренний dispatch всегда использует `execution()`, с фабрикой исключений
или без неё. `sendInContext()` остаётся публичным фасадом с правилами выдачи ошибок `send()`.
Его async-пара `sendInContextAsync($request, $parent, $role)` возвращает
`ResultPromiseInterface<ResultHandle>` и передаёт родительский `PipelineContext`
дочернему исполнению. Оба фасада сохраняют связь trace и наследуют дедлайн родителя; прежде чем
читать результат async-вызова, дождитесь промиса.

## Логические области исполнения <a id="section-4"></a>

`createScope(?string $requestClass = null, ?ExecutionTrace $parent = null,
?string $traceId = null): ExecutionScope` создаёт новую область в состоянии Created
с часами, logger и настройками корреляции клиента. Декоратор делегирует метод без изменений.
Владелец собственного оркестратора вызывает `start()` и `finish()` ровно один раз;
остановленный ленивый обход использует `abandon()`. Не завершайте область запроса,
которой владеет исполнитель.

Прямой paginator/iterator и await владеют отдельными логическими областями.
Пагинацию через клиент завершает его исполнитель. Batch/pool без родителя объединяют
независимые корневые результаты. Подробнее: [трассировка](../results/observability.md),
[выдача ошибок](../results/exceptions.md).

## Ожидающие Promise и Fiber приложения <a id="section-5"></a>

Ожидание из основного стека продвигает цикл до завершения запрошенного SDK Promise.
Это не гарантирует, что каждая ожидающая его Fiber уже возобновилась: её продолжение
может оставаться в очереди. Правило одинаково для SDK-задач и Fiber приложения.
Если важно завершение потребителей результата, дождитесь их собственных Promise;
их можно объединить через `Utils::all()`.

Один `Fiber::start()` не поддерживает работу цикла событий. Для собственных Fiber
приложение должно продвигать свой цикл до их завершения. SDK работает внутри уже
запущенного Revolt через suspension; он не вызывает `EventLoop::run()` и не ждёт
завершения посторонней работы перед возвратом результата.


Для backoff или попыточного поведения используйте [политику задержки или транспортный декоратор](../execution/retry.md#delay-policy).
Отправка остаётся за единой границей допуска HTTP.
