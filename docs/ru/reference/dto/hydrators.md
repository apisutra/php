# Пользовательская гидратация DTO <a id="section-1"></a>

Используйте `DtoHydratorInterface`, если объекты ответа должна создавать существующая
фабрика или mapper приложения, в том числе через private-конструкторы. Обычные DTO
с атрибутами не требуют обработчика. Сериализация остаётся отдельным направлением.

[Полный исполняемый пример](../../../example/dto-hydrator/run.php) объединяет
[фабрику](../../../example/dto-hydrator/src/UserFactory.php),
[гидратор](../../../example/dto-hydrator/src/UserHydrator.php), штатные вложенные DTO,
явную сериализацию и ошибку страницы при ленивом потреблении элементов.

## Контракт и настройка <a id="contract"></a>

Интерфейс находится в `ApiSutra\Contracts\Interfaces\Serialization`:

```php
use ApiSutra\Serialization\Context\HydrationContext;

// Методы DtoHydratorInterface; $dtoClass имеет тип class-string.
public function supports(string $dtoClass): bool;
public function hydrate(array|object $data, string $dtoClass, HydrationContext $context): object;
```

`supports()` не должен выполнять I/O или иметь побочные эффекты. `false` выбирает
штатную гидратацию. Исключение, неверный тип объекта или null не означают fallback.

Классы следующего примера взяты из исполняемого примера по ссылке выше:

```php
use ApiSutra\Config\ClientConfig;
use ApiSutra\Config\HydrationConfig;
use Example\DtoHydrator\UserFactory;
use Example\DtoHydrator\UserHydrator;

$config = new ClientConfig(
    baseUrl: 'https://api.example',
    hydration: new HydrationConfig(hydrator: new UserHydrator(new UserFactory())),
);
```

`HydrationConfig::hydrator` принимает готовый экземпляр, по умолчанию null. Зависимости
создаёт приложение. Обязательные логгер, часы или клиент SDK гидратору не нужны.

Для отдельного запроса используется `Returns::hydrator`:

```php
use ApiSutra\Attributes\Http\Get;
use ApiSutra\Attributes\Response\Returns;
use ApiSutra\Core\AbstractRequest;
use Example\DtoHydrator\User;
use Example\DtoHydrator\UserHydrator;

#[Get('/user')]
#[Returns(User::class, hydrator: UserHydrator::class)]
final class GetMappedUser extends AbstractRequest {}
```

| Значение | Выбор |
| --- | --- |
| null или не указано | Наследуется HydrationConfig::hydrator |
| Имя класса | Заменяет общий обработчик для этого ответа |
| false | Штатная гидратация всего ответа |

Выбранный обработчик действует на граф ответа, включая вложенные DTO и элементы
страницы. Неподдерживаемые типы обрабатывает ядро, а не прежний общий гидратор.
Каждый дочерний HTTP-запрос выбирает свой обработчик. Цепочек приоритетов и discovery нет.

Class-string гидратора в Returns разрешается через доступный provider контейнера;
class-string каста создаётся напрямую без аргументов. Laravel может автоматически
собрать гидратор и конкретную фабрику без регистрации обоих классов. Интерфейсы и
особые параметры требуют обычных bindings приложения. Без контейнера локальный
обработчик должен иметь конструктор без обязательных аргументов; иначе передайте
готовый экземпляр в HydrationConfig. Неверный класс или неразрешимая зависимость дают
`configuration_error`, без скрытого выбора другого обработчика. Декларации классов
DTO и гидратора [проверяются до HTTP](../attributes/response.md#declaration-validation).
Создание обработчика через DI остаётся отложенным до необходимости гидратации,
поэтому ошибка создания зависимостей всё ещё возможна после успешного HTTP-ответа.

## Владение графом и контекст <a id="context"></a>

Стандартный JSON-путь проверяет объектную форму выбранного DTO до вызова
пользовательского гидратора, учитывая локальное разрешение пустого списка.
Гидратор получает обычные PHP-массивы/объекты и сам отвечает за внутренние поля;
готовые объекты повторно не обходятся.
[Форма и границы преобразований](shapes.md#section-3).

Обработчик получает данные после HTTP-декодирования, BeforeHydrate и unwrap, до
штатной обработки полей данного узла. Создание и проверка объекта принадлежат ему.
ApiSutra не применяет повторно computed, policy/casts из DtoHydrationProfileInterface,
атрибуты и внешние правила полей к готовому объекту. При `supports() === false`
все штатные правила работают как прежде. Например, профиль перевода строк в верхний
регистр действует на штатный DTO; пользовательский DTO сохраняет строку своей фабрики.
BeforeHydrate/AfterHydrate и финальная проверка Returns сохраняют HTTP-обязанности.

Наличие любого глобального гидратора отключает предварительную компиляцию внешних
правил DTO при создании Hydrator; supports() на этапе сборки не вызывается.
При supports=false штатные правила проверяются при первом использовании класса
штатным путём, с прежней конфигурационной ошибкой. Для пользовательских узлов
неиспользуемые штатные правила могут вообще не проверяться. Это не отключает
проверку правил, которые действительно использует штатный путь.

Вложенные объекты создавайте через текущий контекст:

```php
// Внутри hydrate(), после проверки $data['address'] и $data['items'].
use Example\DtoHydrator\Address;
use Example\DtoHydrator\User;

$address = $context->hydrate($data['address'], Address::class);
$items = $context->hydrateCollection($data['items'], User::class);
$http = $context->http();
$version = $http?->response?->header('X-Api-Version');
```

Address и User — модели исполняемого примера. Для каждого ребёнка снова
рассматривается выбранный обработчик; вызов hydrate для того же узла не является
штатным fallback и может привести к рекурсии. Штатный родитель может содержать
пользовательские дочерние DTO, а пользовательский родитель — поручать детей ядру.

`http(): ?HttpMappingContext` — сокращение для
`extension(HttpMappingContext::class)`: тот же объект без I/O и второго снимка.
Доступны request, response, traceId, role, runtime options и параметры пагинации.
Оба способа подчиняются [времени жизни контекста](scope.md). В standalone и финальном
payload continuation HTTP-расширения может не быть; тогда http() возвращает null.
После завершения обработчика любой метод контекста выбрасывает исключение.

Экземпляр из конфига может переиспользоваться, как и binding контейнера. Не храните
текущие данные, запрос или контекст в обработчике. Каждый вызов получает собственный
контекст, в том числе при конкурентном исполнении. Локальный класс разрешается один
раз на ответ и используется для контейнера и items. Metadata cache хранит декларации,
а не обработчики.

## Другие входы и ошибки <a id="failures"></a>

- `Hydrator::forConfig($config)` использует тот же обработчик без HTTP и контейнера.
  DTO::from и Hydrator::default не читают общую настройку клиента.
- Cache hit заново гидратирует сохранённый HTTP-ответ. Raw, скачивание и конечный
  response handler сохраняют свои точки выхода; API не добавляет декодирование XML.
- Composite-агрегат использует свою декларацию. Финальный DTO continuation использует
  обработчик клиента, а не обработчик исходного подтверждения операции.
- Внутренние OAuth token DTO явно выбирают штатный путь: прикладной обработчик
  не может обойти нормализацию ответа с токенами.
- Ошибка обработчика и неверный тип результата дают `hydration_error`; для корневого
  несовпадения действуют Returns::mismatchMessage и фабрика исключений результата.
  Управляющие исключения отмены и дедлайна сохраняют смысл.
- Диагностика сохраняет безопасные типы и пути. Пользовательское преобразование
  отмечает границу происхождения; внутренний mapping не выдаётся за точный JSON Pointer.
  Произвольные сообщения исключений не копируются в логи SDK. Собственное логирование
  обработчика не получает автоматически redaction клиента.
- Работа обработчика входит в гидратацию и общий бюджет. Блокирующий код пользователя
  нельзя прервать посередине; новая HTTP-попытка или трасса не создаётся.

Пользовательская гидратация не меняет DTO::toArray(): явная сериализация следует
объявленным выходным правилам DTO. [Ленивое чтение элементов](../execution/pagination-items.md)
сохраняет эти объекты при обходе страниц.
