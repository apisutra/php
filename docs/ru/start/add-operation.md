# Добавить операцию в SDK <a id="section-1"></a>

Сначала найдите существующий клиент и похожую операцию. Используйте их конфигурацию,
правила DTO, ресурсную структуру и способ тестирования.

## Исходные данные <a id="section-2"></a>

Нужны подтверждённые method/path, параметры, auth scope, успешный ответ и хотя бы
один ошибочный ответ. Определите, является ли операция обычной, постраничной,
файловой или запускающей задачу с последующим ожиданием.

## Выполнение <a id="section-3"></a>

1. Разместите запрос и собственные DTO в каталоге операции; общие типы используйте
   по [правилам владения](../guides/sdk/design.md).
2. Опишите вход по [практике запросов](../guides/requests.md): path, query, body,
   варианты oneOf и локальная валидация. Проверьте отсутствие лишних полей на проводе.
3. Добавьте метод ресурса, который возвращает запрос с привязанным клиентом.
   [Учебный ресурс](../../example/sdk/src/Resources/Records/RecordsResource.php) показывает этот шаг.
4. Задайте `Returns`, unwrap и [DTO](describe-dto.md); по фикстуре проверьте типы,
   nullable, отсутствующие поля и неизвестные данные.
5. Добавьте [тесты](../guides/testing/unit.md): подготовленный запрос, успешный DTO,
   ошибка API, нарушенная форма ответа. Повторные попытки проверяйте только при
   подтверждённой повторяемости операции.
6. Добавьте операцию в документацию SDK и [карту покрытия](../guides/sdk/coverage.md).

## Проверка результата <a id="section-4"></a>

Операция вызывается публичным методом ресурса, использует существующего клиента,
отправляет ожидаемый HTTP-запрос и возвращает документированный результат. В тестах
нет случайного HTTP и скрытой зависимости от контейнера. Добавленные типы не
создают конкурирующих моделей одной сущности без объяснимого различия контракта.

Для особых операций: [пагинация](../guides/recipes/pagination.md),
[ожидание](../guides/recipes/continuation.md), [файлы](../guides/recipes/files.md).
