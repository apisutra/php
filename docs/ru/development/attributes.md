# Устройство атрибутов <a id="section-1"></a>

Как ядро читает, кеширует и обрабатывает атрибуты. Публичные декларации находятся
в [справочнике атрибутов](../reference/attributes/README.md), а места вызова
обработчиков — в [пайплайне](pipeline.md#section-7).

## Роль атрибутов <a id="section-2"></a>
Атрибуты — декларативный слой конфигурации запросов и DTO. Они позволяют описывать:
- HTTP‑метод и endpoint
- источники данных (query/body/path/header/file)
- правила валидации и трансформации
- поведение пайплайна (cache/retry/timeout/ratelimit)

## Где используются <a id="section-3"></a>
- **RequestSpecResolver** — собирает метаданные запроса (HTTP, responseType, behavior).
- **Serializer** — применяет request‑атрибуты для сборки PreparedRequest.
- **Hydrator** — применяет DTO‑атрибуты при гидрации.
- **HookRunner** — исполняет hook‑атрибуты.
- **AttributeRegistry** — запускает кастомные обработчики атрибутов.

## Резолв и кеш <a id="section-4"></a>
- [MetadataCatalog](../../../src/Metadata/MetadataCatalog.php) выполняет общий обход свойств.
  `ClassMetadata` хранит свойства как `ReflectionProperty`: это готовые рецепты с declaring class,
  native-типами и модификаторами; состояние конкретного объекта проверяется при чтении.
- `AttributeMetadataCache` владеет общим каталогом структуры. Направленные
  планы `:hydration-plan`, `:serialization-plan` и `:request-parts-plan` выбирают свои атрибуты и
  проверяют применимость в прежних точках. Параметры конструктора читаются только
  для входного плана, их defaults при discovery не вычисляются.
  [Входные планы](hydration.md) разделяются по проверенному описанию правил в WeakMap;
  общий каталог не хранит policy клиента или результаты живого профиля.
- `warmup()` использует тот же каталог. Общий ключ класса остаётся адаптером
  `AttributeRegistry` с рецептами в Reflection-порядке, а не планом преобразования.
  Прогрев не создаёт пользовательские аргументы атрибутов, profiles или handlers.
- В гидраторе и сериализаторах значения атрибутов с объектными аргументами создаются
  для текущего узла; scalar/enum и массивы значений позволяют переиспользовать шаблон.
  Defaults конструктора вычисляет PHP при пропущенном аргументе.
- Клиент отключает кеш в `Environment::Local/Testing` и включает в Production.
  `Hydrator::default()` обнаруживает атрибутные декларации без config; `Hydrator::forRules()` создаёт собственный
  включённый кеш. Результат изоляции объектов от режима кеша не зависит.

Момент вызова пользовательского конструктора различается для
[default DTO](../reference/dto/lifecycle.md#section-3) и
[аргумента атрибута](../reference/dto/lifecycle.md#section-2).
Кеш метаданных не предназначен для общего изменяемого состояния.

### Публикация правил DTO <a id="section-5"></a>

`RuleSetCompiler` принадлежит своей конфигурации. Он хранит готовые описания отдельно
от черновиков текущего корня. Внутренние ссылки `Node → Node` и `A → B → A` могут
читать черновик; исполнителю становится доступна только целиком проверенная группа.
Нативный object-тип сам по себе не запускает компиляцию дочернего DTO.

Внешний повторный вызов для ещё неготового класса во время компиляции, в том числе
из Fiber/autoload, получает `ConfigurationException`. Уже готовые описания доступны.
Отказ повторному входу не портит приостановленную операцию. На поле DTO отдельный
автомат не создаётся: жизненным циклом управляет сам компилятор.

После ошибки черновики удаляются. Ошибка до создания первого `CompiledDtoRules`
сохраняет прежние готовые записи; ошибка после этого рубежа очищает готовые правила
и receiver-кеш владельца. Структурный каталог остаётся пригодным. Ошибки не кешируются,
следующий вызов проверяет декларацию заново. Отключение `AttributeMetadataCache`
не отключает существующую memoization готовых правил.

Проверки: [общая структура и рецепты](../../../tests/Unit/Serialization/MetadataCatalogTest.php),
[рекурсия и отказ](../../../tests/Unit/Serialization/MetadataCompilationTest.php),
[изоляция значений](../../../tests/Unit/Serialization/MetadataValueIsolationTest.php).

## Кастомные атрибуты (AttributeRegistry) <a id="section-6"></a>

[AttributeRegistry](../../../src/Attributes/AttributeRegistry.php) регистрирует соответствия
«класс атрибута → класс обработчика». Resolver реестра создаёт обработчик при первом
обращении; затем его экземпляр переиспользуется. Данные текущего исполнения
передаются через контекст.

### Типы обработчиков <a id="section-7"></a>
- **AttributeHandlerInterface** — простой обработчик:
  получает атрибут, Reflection‑цель и `PipelineContext`.
- **AttributeContextHandlerInterface** — контекстный обработчик:
  получает `AttributeContext` с `PipelineStage`, `type`, `data` и списком
  атрибутов класса; может вернуть модифицированные данные.

### Порядок обхода <a id="section-8"></a>
1) Атрибуты класса
2) Атрибуты свойств
Порядок соответствует Reflection‑порядку объявления.

## AttributeContext <a id="section-9"></a>
Контекст, который получает обработчик:
- `attribute` — инстанс атрибута
- `target` — ReflectionClass или ReflectionProperty
- `type` — Request/Dto
- `stage` — PipelineStage
- `context` — PipelineContext
- `data` — текущие данные (если обработчик работает со стадией)

## StageProcessor <a id="section-10"></a>

`StageProcessor` связывает Pipeline с `AttributeRegistry::processStage()`.
Фактические точки вызова перечислены в [пайплайне](pipeline.md#section-7).
Контекстный обработчик может возвращать изменённые данные, которые передаются
следующему обработчику; вызывающая стадия определяет, как использовать итог.
Записи стадий в audit не запускают обработчики автоматически.

Регистрацию и передачу данных проверяет
[AttributeRegistryTest](../../../tests/Unit/Attributes/AttributeRegistryTest.php).

## Ограничения <a id="section-11"></a>
- Атрибуты не должны выполнять бизнес‑логику.
- Тяжёлые вычисления выносить в сервисы/хуки.
