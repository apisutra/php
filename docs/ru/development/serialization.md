# Исполнение исходящей сериализации <a id="section-1"></a>

Выход имеет общий план структуры и общий выбор преобразования значения. Политики
DX, явно заданной сериализации и HTTP задаются на входах. Пользовательский контракт
описан в [справочнике сериализации](../reference/serialization/README.md).

## Владельцы решений <a id="section-2"></a>

| Компонент | Ответственность |
| --- | --- |
| [SerializationPlanCompiler](../../../src/Serialization/Plan/SerializationPlanCompiler.php) | Выбирает выходные декларации из MetadataCatalog, проверяет видимость, публикует готовый план |
| [SerializationPlan](../../../src/Serialization/Plan/SerializationPlan.php) | Хранит шаблоны полей и Reflection-рецепты; материализует объектные args для текущего узла |
| [SerializationFieldPlan](../../../src/Serialization/Plan/SerializationFieldPlan.php) | Задаёт чтение поля и выбор выходного имени: To → Map → текущая naming policy |
| [SerializationValuePlan](../../../src/Serialization/Plan/SerializationValuePlan.php) | Хранит кандидаты объявленного типа и описание Cast; выбирает тип по текущему значению |
| [DtoSerializer](../../../src/Serialization/DtoSerializer.php) | Связывает план с policy/registry, защищает активную ветвь, читает поля, пропускает null и записывает результат |
| [SerializationValueResolver](../../../src/Serialization/SerializationValueResolver.php) | Исполняет приоритеты Cast/DTO/array/type/enum/date/object для DTO и query/body |
| [ReceiverOutput](../../../src/Serialization/Rules/ReceiverOutput.php) | Проверяет видимый receiver перед cast и строит представление без receiver |

Эти типы планов внутренние. Они не являются новым DSL или точкой регистрации
пользовательских стадий; декларации DTO и публичные фасады остаются прежними.

## Компиляция и привязка к вызову <a id="section-3"></a>

Кеш плана использует тот же переключатель AttributeMetadataCache и отдельный ключ
`:serialization-plan`. В нём нет экземпляров DTO, обработчиков, результатов
profile.policy()/casts() или объектных аргументов. Безопасные значения деклараций
нормализуются; аргумент с `new` остаётся Reflection-рецептом.
Это плоское описание полей: оно не разрешает дочерние классы и не содержит config.
Граф правил и receiver принадлежат RuleSetCompiler с отдельной
[границей публикации](attributes.md#section-4).

Первый вызов читает свойства по порядку и материализует декларации в прежней точке.
План публикуется после успешного прохода. Повторный вызов материализует все объектные
аргументы до чтения первого значения, включая null и поле, которое будет пропущено.
Ошибка рецепта не оставляет объекты в кеше; следующий корневой вызов может повторить
исполнение. Изменённый профиль и намеренно общий handler сохраняют своё поведение.

PropertyTypeInspector разрешает относительные native-имена по declaring class;
то же правило используют вход, итоговые проверки и Nested. План сохраняет
разрешённые имена кандидатов, но не фиксирует runtime-ветвь. Одно поле может
содержать разные варианты union, DTO или массив. Сложный тип, который прежний
PropertyTypeInspector разбирает только при обращении, сохраняет эту отложенную границу.

## Порядок исполнения <a id="section-4"></a>

| Вход | Привязка |
| --- | --- |
| serialize / toArray | Receiver discovery при включённой конфигурации → профиль → защита DTO → материализация → поля; дочерний DTO разрешает свой профиль |
| serializeWithPolicy | Явные policy/registry → защита DTO → материализация → поля с receiver-проверкой; дочерний DTO наследует policy/registry |
| HTTP DTO | Serializer обнаруживает receiver, разрешает wire-профиль и вызывает serializeWithPolicy |
| Query/body запроса | [RequestPartsPlan](request-serialization.md) задаёт размещение; collector передаёт value plan в общий resolver |

Значение читается непосредственно перед преобразованием поля: предыдущий callback
может изменить следующее поле или общий registry. Resolver переиспользуется в узле,
но выбранный handler не кешируется вместо обращения к живому registry.
Header/path/file сохраняют собственные адаптеры и не получают полный Cast/DTO-путь.

## Receiver: проверка и проекция <a id="section-5"></a>

Перед выбранным пользовательским cast выполняется отдельная проверка наличия receiver.
Она сохраняет отказ до создания и вызова handler; объектные args к этому моменту уже
могли быть созданы при чтении metadata. Для DX и explicit policy порядок ранних ошибок
может различаться — это часть действующего контракта.

Для массива сначала преобразуются DTO и enum, затем ReceiverOutput обходит готовое
представление. Обходы намеренно разделены: поздний callback способен добавить receiver
в ранее посещённый plain-объект. Слияние проходов или кеш результата по object id
пропустили бы это изменение. Opaque-объекты сохраняют свою границу; исходные plain-объекты
ядро не изменяет. Повторные ссылки в соседних ветвях допустимы.

[Состояние обхода](architecture.md#section-13) и контексты
обработчиков общие по устройству, но лимиты DTO, массивов и receiver остаются разными.

## Проверка изменений <a id="section-6"></a>

[SerializationPlanTest](../../../tests/Unit/Serialization/SerializationPlanTest.php) проверяет
живые профили, общий кеш, union, изменения registry внутри callback, порядок projection
и освобождение args. Проверки metadata isolation, контекстов, receiver, частей запроса
и циклов дополняют его. Одного совпадения JSON недостаточно: сохраняйте trace,
исключения и измеряйте cold/warm/cache-off отдельно от инструментирования обходов.

Стоимость холодного плана включает создание описаний полей. Для поля без деклараций
общий reader пропускает отдельный поиск каждого атрибута; простой native-тип
нормализуется без промежуточного списка кандидатов. Эти сокращения не кешируют
значения вызова и не меняют моменты создания объектных args.
